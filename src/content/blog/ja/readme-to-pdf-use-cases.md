リポジトリのリンクは、すでにGitHubを使っている人にドキュメントを共有するには優れた方法です。それ以外の人に共有するには不向きです。レビュアーは文脈を失い、クライアントはアカウントを作りたがらず、URLはアーカイブではありません。PDFは配布の問題を解決しますが、それは意図をもって作成された場合に限ります。

md2pdfは狭いワークフローを中心に作られています。公開リポジトリ、ローカルファイル、またはクリップボードからMarkdownを取得し、GitHub Flavored Markdownでレンダリングし、印刷用スタイルシートを適用し、ブラウザの「PDFとして保存」ダイアログに渡します。この狭さが役に立ちます。同じツールが、サーバーもアカウントもアップロードもなしに、5ページのクライアント引き継ぎ資料にも50ページのコースリーダーにも対応できるということです。

以下では、このワークフローが力を発揮する7つの場面と、それぞれを機能させるための設定と準備を紹介します。

## 1. クライアントやステークホルダーへの引き継ぎ

クライアントがプロジェクト概要を読むためだけにリポジトリへのアクセスを望むことはほとんどありません。求めているのは、開いて、同僚に転送し、会議で注釈を付けられる文書です。README PDFは多くの場合、適切な詳細レベルです。スコープ、アーキテクチャのメモ、セットアップ手順、スクリーンショット、既知の制限が1つのファイルに収まります。

**推奨設定：**

- テーマ：外部向けなら**ビジネス**、非常に技術的なクライアントなら**クリーン**。
- 目次：4ページを超える文書ではオン。
- ページサイズ：クライアントの地域に合わせる。ヨーロッパとアジアの多くはA4、米国とカナダはレター。
- ソース：公開リポジトリなら取得。そうでなければMarkdownを貼り付けるかREADMEファイルをアップロード。

**重要な準備：**

- エクスポート前に社内チケットのリンク、ステージングURL、認証情報を削除します。ツールは文書をアップロードしませんが、PDFは転送できるファイルです。
- 相対画像パスを、実際に存在するリポジトリのパスに置き換えます。md2pdfはリポジトリ取得時に解決しますが、壊れたソース画像はPDFでも壊れたままです。
- READMEが変更履歴ではなく要約から始まっているか確認します。引き継ぎ文書は、何が変わったかを伝える前に、プロジェクトが何であるかを読者に伝えるべきです。
- READMEがセットアップ手順とアーキテクチャの背景を混在させている場合は、「この文書の読み方」という短い段落を追加します。

クライアントがレビューで特定のページを参照する場合は、ブラウザのページ番号オプションを使用してください。アプリの印刷用スタイルシート自体はページ番号を追加しません。ブラウザのヘッダーとフッターが最も簡単な方法です。

## 2. オフラインアーカイブとリリースドキュメント

リポジトリにだけ存在するドキュメントは、読者の足元で変わります。ある時点のリリースがどうだったかのスナップショットが必要なとき、PDFは安定した成果物です。バイナリの隣に保存したり、リリース記録に添付したり、将来のREADME書き換えを気にせずプロジェクトアーカイブに保管したりできます。

**推奨設定：**

- テーマ：**クリーン**。
- 目次：オン。
- ファイル名：リポジトリ、リリースタグまたはコミット、日付を含めます。例：`acme-api-v2.4.0-readme-2026-10-02.pdf`。
- ソース：公開リポジトリを取得し、意図したREADMEをエクスポートしているか確認します。アプリは既定ブランチを読むため、特定のタグやコミットに固定したい場合は貼り付けの経路を使ってください。

**重要な準備：**

- ソースを文書内かファイル名のどこかに記録します。バージョンのないPDFは、日付のない添付ファイルにすぎません。
- アーカイブ前にリンクを確認します。blobリンクはリポジトリの既定ブランチを指し続けます。タグやコミットの真のスナップショットが必要な場合は、取得フローではなくそのバージョンのREADMEを貼り付け、コミットハッシュをフッター行か付随するリリース記録に記載してください。
- ブラウザのヘッダーとフッターにローカルファイルパスや社内ホスト名が含まれる場合は無効にします。アーカイブは自己完結しているべきで、作成したマシン情報を漏らすべきではありません。
- アーカイブの再現性が必要な場合は、MarkdownソースをPDFと一緒に保管します。PDFは成果物、Markdownはレシピです。

これはレビュー中の**ダーク**テーマにも適した用途です。画面でプレビューを読み、印刷用スタイルシートが紙用に明るくすることを理解したうえでエクスポートします。画面の見た目が印刷結果だと思い込まず、最終PDFを確認してください。

## 3. 学術提出とコースパック

学生や講師は、Markdownのノート、プロジェクトドキュメント、読書資料を1つの文書として提出または配布する必要があることがよくあります。アカデミックは製品READMEとは異なる役割を担います。ゆとりのある文章、控えめなコードブロック、ランディングページに見えないレイアウトが必要です。

**推奨設定：**

- テーマ：**アカデミック**。
- 目次：3つ以上のセクションがある場合はオン。
- ページサイズ：所属機関の要件に従う。米国外ではA4が一般的で、米国ではレターが一般的。
- ソース：作品が公開されていない場合はMarkdownをアップロードまたは貼り付け。変換のためだけに未公開作品を公開リポジトリに置かないでください。

**重要な準備：**

- エクスポート前に見出し階層を確認します。レベルを飛ばしたコースリーダーは目次が混乱します。
- アカデミックは本文を両端揃えにします。非常に長いURL、コード識別子、数式は不自然な間隔を生むことがあります。長いURLは参照スタイルのリンクに分けるか、脚注のようなセクションに移してください。
- コードブロックは短く保ちます。テーマは印刷に適した明るいコード背景を使いますが、120文字の行はやはりページからあふれます。
- 文書に引用を含める場合は、Markdown内の参考文献セクションとして保持します。md2pdfはテキストをレンダリングするだけで、引用スタイルは管理しません。
- 提出前に草案を印刷します。両端揃えのテキストとセリフ書体は、プレビューと紙で印象が変わることがあります。

変換はクライアントサイドで行われるため、未公開のノートや論文の草案がブラウザから出ることはありません。これは「文書を当社のコンバーターに貼り付けてください」というサービスに対する明確な利点です。

## 4. 社内レビュー資料とリリースノート

エンジニアリングチームは、設計レビュー、リリース準備確認、インシデント後のフォローアップのために1つの文書を必要とすることがよくあります。ソースはすでにREADMEやドキュメントページとして存在しているかもしれません。PDFにすることで、会議の議題と、レビュアーが何を見たかの記録が固定されます。

**推奨設定：**

- テーマ：エンジニアリングレビューなら**クリーン**、部門横断の読者なら**ビジネス**。
- 目次：オン。
- ソース：公開リポジトリの取得、または非公開ならMarkdownを貼り付け。

**重要な準備：**

- 決定事項や依頼を冒頭に置きます。3ページの背景から始まるレビュー資料はレビューされません。
- 未解決の質問を明示します。PDF形式は印刷したコピーに注釈を付けやすいですが、それは質問が見えている場合に限ります。
- 秘密情報と顧客識別子を削除します。ツールは文書をどこにも送信しませんが、レビュー資料は転送されがちです。
- ファイル名にコミットまたは文書バージョンを含めます。バージョンのないレビューノートは後で照合しにくくなります。
- 文書にタスクリストが含まれる場合は、レンダリングを確認します。GitHub Flavored Markdownのタスクリストには対応していますが、長いチェックリストはページをまたいで分割されることがあります。関連する項目はまとめておいてください。

非公開リポジトリは取得フローではサポートされません。社内作業では、貼り付けまたはアップロードの経路が現実的な選択です。これは製品に後付けした回避策ではなく、公開URLから読むべきでない資料を扱うための意図された方法です。

## 5. ワークショップ資料とカンファレンス資料

リポジトリにあるワークショップの演習は、ネットワークアクセス、GitHubアカウント、動作するノートPCを前提とします。印刷された配布資料はそのどれも前提としません。チュートリアル、カンファレンスセッション、教室での実習では、PDFが会場で最も信頼できるコピーであることがよくあります。

**推奨設定：**

- テーマ：洗練された配布資料なら**ビジネス**、コードの多い実習なら**クリーン**。
- 目次：複数の演習がある場合はオン。
- ページサイズ：会場のプリンターに合わせる。A4とレターはどちらも一般的なので、50部印刷する前に確認してください。
- ソース：公開ワークショップリポジトリなら取得、非公開の草案ならアップロード。

**重要な準備：**

- グレースケールを前提に設計します。色だけに頼ってセクションを区別するテーマは、白黒プリンターでその区別を失います。
- コード行はおよそ80文字未満に保ちます。配布資料は27インチモニターではなく、腕を伸ばした距離で読まれます。
- 読者が最新版を必要とする場合は、公開リポジトリへの短いURLやQRコードを追加します。PDFは安定したコピー、リポジトリは生きたコピーです。
- ページ数を確認します。40ページの配布資料は6ページの演習シートとは別物です。目次と見出しを使って、何を含めるかを決めてください。
- イベント前に1部印刷します。画面では問題なく見えたブラウザの印刷設定が、会場のプリンターでは異なる余白を生むことがあります。

アプリの印刷用スタイルシートはきれいなページ分割のために設計されていますが、特定のプリンターが余白をどう扱うかまではわかりません。1回のテスト印刷が依然として最良の品質確認です。

## 6. 助成金、ポートフォリオ、就職の応募

応募では、プロジェクト概要、技術レポート、ポートフォリオサンプルを1つの添付ファイルとして求められることがよくあります。README PDFはここで有効に機能します。レビュアーがGitHubアカウントなしで開ける形で、プロジェクト自身のドキュメントを示せるからです。

**推奨設定：**

- テーマ：一般的な読者なら**ビジネス**、研究志向の応募なら**アカデミック**。
- 目次：数ページを超える場合はオン。
- ページサイズ：応募要項に従う。
- ソース：公開リポジトリを取得、または非公開ならMarkdownを貼り付け。

**重要な準備：**

- 最も関連するプロジェクトを最初に置きます。応募のレビュアーは最初の2ページしか読まないことがあります。
- 意味を加えないバッジを削除します。ビルドバッジの壁はポートフォリオの添付資料ではノイズです。
- スクリーンショットや図に代替テキストがあり、実際に表示されることを確認します。壊れた画像は画像なしより悪いです。
- PDF内のリンクがクリックできるか確認します。公開プロジェクトへクリックできないレビュアーは文脈を失います。
- ファイルサイズを適切に保ちます。画像の多い非常に大きなPDFは、応募ポータルのアップロード上限に達することがあります。

これは**ビジネス**テーマのセリフ書体が、技術プロジェクトを生のリポジトリダンプではなくプロフェッショナルな文書として読ませるのに役立つケースでもあります。内容が応募を支える必要があるのは変わりません。テーマは雰囲気を設定するだけです。

## 7. 監査とコンプライアンスのスナップショット

PDFの目的が最初から最後まで読まれることではない場合もあります。特定の日付にドキュメントが何を述べていたかを証明することです。アクセス制御、データ処理、運用手順を説明するREADMEは、不変の成果物として保存されていれば、監査パッケージの有用な一部になり得ます。

**推奨設定：**

- テーマ：**クリーン**。
- 目次：長い文書ではオン。
- ファイル名：リポジトリ、コミット、取得日を含める。
- ソース：公開リポジトリを取得、またはレビュー済みのMarkdownをそのまま貼り付け。

**重要な準備：**

- ソースのバージョンを記録します。コミット参照のないPDFは弱い証拠です。元のREADMEは変わり得るからです。
- PDFを記録のシステムとして扱わないでください。これはドキュメントのスナップショットであり、ログ、ポリシー、署名済み証明の代わりではありません。
- 文書に秘密情報、社内ホスト名、個人データが含まれていないか確認します。監査パッケージは元のリポジトリより広く共有されることがよくあります。
- MarkdownソースとPDFを一緒に保管します。取得内容に疑問が呈された場合、ソースが成果物の作成方法を説明します。
- ソースが変わったら再エクスポートします。現在のファイル名を付けた古いPDFは、明らかに日付の古いPDFより悪いです。

## PDFが適切でない形式である場合

PDFは配布形式であり、共同作業の形式ではありません。次の場合は不適切な選択です。

- 文書が毎日変わり、読者が最新版を必要としている。代わりにリポジトリへリンクするか、定期的にPDFを生成してください。
- 内容がインタラクティブな要素、ライブデータ、埋め込み動画に依存している。PDFはそれらをすべて平坦化します。
- リポジトリが非公開で、受け取る人がソースを閲覧する必要がある。PDFはスナップショットを渡すだけで、アクセス権は渡しません。
- 文書が1ページの短いもので、リポジトリで十分読める。余分な手間に見合わないかもしれません。
- コメントや提案の追跡が必要。共同編集ツールを使ってください。PDFの注釈はレビューワークフローの代わりにはなりません。

このツールは意図的にドキュメントプラットフォームではありません。すでに持っている文書を、持ち運べる文書に変換するものです。使うべきでない場面を知ることも、うまく使うための一部です。

## 5分間の事前チェックリスト

| 確認項目 | 重要な理由 |
| --- | --- |
| ソースが正しいリポジトリまたはファイル | 間違ったプロジェクト名のPDFは、PDFがないより悪い |
| 見出し階層が一貫している | 目次とページ構造を左右する |
| 画像が表示される | リポジトリ相対パスにはリポジトリ取得が必要 |
| コード行が広すぎない | 幅の広いコードブロックは最もよくある切れ目の問題 |
| 表がページに収まる | 8列の表がA4に収まることはほとんどない |
| リンクが意味を成す | blobリンクと外部リンクはオフラインでも理解できるべき |
| 機密テキストが削除されている | 変換がローカルでもPDFは転送できる |
| テーマが読者に合っている | エンジニアにはクリーン、クライアントにはビジネス、文章にはアカデミック |
| ページサイズが受け取る人に合っている | A4とレターでページ分割が変わる |
| ファイル名にバージョンが含まれている | 成果物を追跡可能にする |

## テーマ早見表

- **クリーン** — 仕様書、技術README、コードの多い配布資料、監査。
- **ビジネス** — クライアントへの引き継ぎ、提案書、ワークショップ資料、ポートフォリオ添付。
- **アカデミック** — コースパック、論文、長文の文章、研究応募。
- **ダーク** — エクスポート前の画面レビュー。印刷用スタイルシートが紙用に明るくします。

迷ったらクリーンから始め、1部エクスポートして、スマートフォンか印刷したページで読んでみてください。大きなモニターで最も良く見えたテーマが、腕を伸ばした距離で最も読みやすいとは限りません。

印刷設定とトラブルシューティングを含む完全なワークフローは[GitHubのREADMEをPDFに変換する方法](/blog/github-readme-to-pdf/)をご覧ください。4つのテーマを詳しく知りたい場合は[クリーン vs ビジネス vs アカデミック vs ダーク](/blog/readme-pdf-print-themes/)をご覧ください。
